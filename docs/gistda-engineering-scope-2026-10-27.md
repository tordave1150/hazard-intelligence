## Concrete next implementation

`scripts/gistda_candidate.py` implements a fixed **1day / Ongkharak ap_idn=2604** collector in memory. It makes one header-authenticated request, `limit=100`, `offset=0`, with no retries, redirects, alternate window or pagination. The 100-feature cap is a local development bound, not an ArcGIS limit or a claim about the Features service maximum. JSON is capped at 2 MiB and aggregate geometry at 20,000 positions. The returned counts must confirm the whole query fits that one response; otherwise it is rejected, never published as a partial district snapshot.

The candidate retains only validated Polygon/MultiPolygon coordinates, generated internal feature IDs, attribution, the exact product/filter and response/retrieval times. It verifies source province/district identities and finite, valid, bounded geometry. Unknown satellite acquisition is explicitly null. Unverified area/exposure fields, creator identifiers, raw properties, links/assets and echoed keys are discarded. No satellite coverage, clipping quality, water depth, severity, affected population or no-flood inference is made. The CLI emits only a value-free receipt, including genuine zero results, and never exports geometry or writes Atlas.

`.github/workflows/gistda-candidate.yml` runs on a manual main invocation or an explicit main change to `.github/gistda-candidate-request.json`. The fixed request file contains only a public request ID; it cannot choose an endpoint, key, district or product. The job uses the existing GISTDA secret, contents:read, no MongoDB credentials, no upload artifact and no schedule. Request **2026-10-27-01** performs the first real candidate validation. Unlike the earlier limit=1 schema inspections, this checks completeness for the fixed district candidate. Real execution evidence is recorded after the run completes.

This is the first adapter stage, not a connected production map.
